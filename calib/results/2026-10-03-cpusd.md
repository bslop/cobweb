# The 68000 on compiled code, SD reads, the Blitter base: platform bench job 211, 2026-10-03

Bench Jaguar (NTSC), GameDrive cart mode. The program is the clean platform repository's
`bench/cpusd` (game-free), built on the released editions `platform-jag-2026-10-02` and
`platform-gd-2026-10-02` with the cobweb-2026-10-05 tools. It runs fixed workloads under three
display set-ups (A no objects, B an 8bpp 320x240 DRAM bitmap, C B plus a 16bpp 320x240 bitmap),
timed in VI fields. Platform issue 0011: a game's 68000-bound run was 11% short in jsim.

| Workload | Silicon A / B / C | jsim 10-05 A / B / C |
|---|---|---|
| alu: 100000 x jcc68k integer arithmetic | 101 / 111 / 133 | 125 / 141 / 169 |
| mem: 10 x 64 KB jcc68k long copy | 121 / 135 / 161 | 142 / 159 / 192 |
| call: 300 x 64 struct updates with calls | 83 / 92 / 109 | 93 / 104 / 125 |
| sd32: CPU-mode `gd_fread`, 32 KB calls, 1 MB | 227 / 228 / 238 | 33 / 32 / 32 |
| sd4: CPU-mode `gd_fread`, 4 KB calls, 512 KB | 120 / 121 / 128 | 25 / 28 / 34 |
| bpc: 200 full-screen 16bpp phrase copies, DRAM to DRAM | 96 / 106 / 126 | 81 / 90 / 107 |
| bpf: 200 full-screen 16bpp phrase fills | 22 / 25 / 30 | 19 / 22 / 26 |
| bxc: 30 pixel-mode copies of 319x200 from x = 1 | 50 / 56 / 66 | 48 / 53 / 64 |
| gpu: one sync GPU-mode read of 737,280 bytes (A) | 155 | 1 |

The display ratios (B/A, C/A) agree. Three separate errors partly cancel on a game frame:
- the 68000 runs compiled code 12-27% slow in jsim;
- SD reads cost the 68000 almost nothing in jsim;
- the Blitter runs phrase-mode copies and fills 13-17% fast.

## The 68000

By the MC68000 User's Manual the alu loop costs 184 clocks an iteration, which would be
83 fields with no waits. Silicon takes 101: +18 clocks for 33 instruction words. jsim took
125, because its instruction timings were per-group constants (every MOVE 8 clocks,
`move.l Dn,Dn` included) under wait constants fitted around them. Also, `fetch32` charged
its two instruction words as data reads.

**Model:** the User's Manual timings (`m68k/exec.rs`, tables 8-1 to 8-10), `fetch32`
counted as two fetches, and the three wait constants refitted by least squares on seven
loops (`M68K_*_WAIT_X10` in `m68k.rs`, with the table): fetch 1.2, read 3.2, write 5.8.
The old values were 1.3 / 5.1 / 10.3. On this ROM, jsim now gives:

| | Silicon A / B / C | jsim A / B / C |
|---|---|---|
| alu | 101 / 111 / 133 | 101 / 113 / 137 |
| mem | 121 / 135 / 161 | 125 / 140 / 169 |
| call | 83 / 92 / 109 | 85 / 95 / 115 |

## SD reads

A CPU-mode `GD_FRead` keeps the 68000 in the vendor's SPI loop. From sd32 and sd4 (with
no display; one seek every 64 KB folded in): **12,900 clocks a call plus 47.6 clocks a
byte**. The sync GPU-mode read: 155 fields for 737,280 bytes, **46.6 clocks a byte**. jsim
charged 20 clocks a call, plus the delivered bytes as if the 68000 had written them.

**Model:** `gamedrive::read_cost`. The 68000 waits it out in 64-clock slices
(`M68k::gd_busy`) and takes interrupts meanwhile, resuming after their RTE. The slices
aren't stretched by the display, since silicon slowed only 0-7% under one. The delivered
bytes no longer count as 68000 bus cycles. On this ROM:

| | Silicon A / B / C | jsim A / B / C |
|---|---|---|
| sd32 | 227 / 228 / 238 | 229 / 230 / 232 |
| sd4 | 120 / 121 / 128 | 121 / 122 / 123 |
| gpu (A) | 155 | 156 |
