# G_HIDATA and register write order: platform bench jobs 395-400, 2026-10-14

Bench Jaguar (NTSC). The program is the clean platform repository's `bench/gpuhaz`
(game-free), built with the cobweb-2026-10-12 tools: a GPU kernel and a DSP kernel, each
run again and again by the 68000, which paints every result as 32 cells on a 16bpp
320x240 screen; captures were decoded by `bench/gpuhaz/cases.py`. Each job captured 8
passes out of 30-45. The display (that bitmap, in DRAM) and the 68000 (polling `G_CTRL`
or `D_CTRL`, then painting) run throughout. Platform issue 0016.

The DRAM pattern: the 16-bit word at byte offset `b` holds `$8000 + b`, so the long at
`$200` is `$82008202` and at `$204` `$82048206`. PRIME is a `loadp` of the phrase at
`$380`: `$83808382` in G_HIDATA and on the upper half of the bus. MARK stores
`$EEEE00nn` into G_HIDATA.

## 1. A MOVE right behind an ALU write of the same register (GPU and DSP)

`r8 = $88, r7 = $700, r6 = $6000` before each case; the result is `r8` (jobs 395-400,
identical on both cores, in every pass).

| Case | Program order | Silicon |
|---|---|---|
| `add r7,r8 / move r6,r8` | $6000 | **$788** |
| `add r7,r8 / moveq #5,r8` | 5 | **$788** |
| `sub`, `addq`, `addqt`, `shlq`, `mult`, `imult` then `move r6,r8` | $6000 | **the ALU result** |
| `add r7,r8 / movefa r6,r8` | $6000 | **$788** |
| `add r7,r8 / move pc,r8` | an address | **$788** |
| `load (r23),r7 / add r7,r8 / move r6,r8` (the add stalls) | $6000 | **$5AE2** |
| `add r7,r8 / move r6,r8 / move r8,r10`: r10, r8 | $6000, $6000 | **$788, $788** |
| `add r7,r8 / moveq #5,r8 / add r7,r8` | $705 | **$E88** |
| `jr ne` falls through; slot `add r7,r8`; `move r6,r8` | $6000 | **$788** |
| the same with `jump ne,(r9)` | $6000 | **$788** |
| falls through; slot `add r7,r8`; `moveq #5,r8` | 5 | **$788** |

| `add r7,r8 / load (own RAM),r8` | $5A5A | $5A5A |
| `load (own RAM),r8 / move r6,r8` | $6000 | $6000 |
| `jr eq` taken; slot `add r7,r8`; target `move r6,r8` | $6000 | $6000 |
| falls through; slot `add r7,r8`; `nop`; `move r6,r8` | $6000 | $6000 |
| falls through; slot `add r7,r8`; `add r6,r8` | $6788 | $6788 |
| falls through; slot `move r7,r8`; `move r6,r8` | $6000 | $6000 |
| `load (DRAM),r8 / move r8,r8 / moveq #5,r8` | 5 | 5 |
| `load (DRAM),r8 / or r8,r8 / nop / moveq #5,r8` | 5 | 5 |
| `add r7,r8 / move r8,r9` (a reader): r9 | $788 | $788 |

So the MOVE's write is lost whenever it is the very next instruction after an ALU op that
wrote the same register, and nothing else. The ALU op writes at cycle 3 and the MOVE at
cycle 2 (TRM), so they write together and the ALU's value stays. It does not matter whether
a jump is involved: a conditional jump that falls through just makes its delay slot and the
next instruction adjacent, and a taken jump's refill separates the slot from the target.
The bug-13 guard `or rN,rN` is an ALU op, so an overwrite straight after it is lost.

`x` marks bytes that changed from pass to pass and build to build: `$0001`, `$0006`, `$0016`,
`$0280`, `$2007`, `$2E00`, `$4A80`, `$6000`, `$6700`, `$FFE0`; `$6700` is a 68000 `beq`
opcode word. So every GPU load from the main bus copies the upper half of the bus into
G_HIDATA when it lands; the bytes the load drives are its own, the rest are whatever any
master last left there. Stores drive the upper half (their data repeated) and don't latch.
Nothing but the GPU's own loads changes G_HIDATA.

## 3. Aside: DSP stores to DRAM (job 399)

In one build the DSP kernel kept its results in DRAM. With the 68000 polling `D_CTRL`
meanwhile, the long results at A%8 = 4 read back as `$FFFF` and the low word of the long
before (4 of 18, every pass of job 399; one in job 396). Kept in DSP RAM (job 400), every
result was right. Not modelled; not investigated further.

## jsim

- `Stats::alu_move_waw` (with the first PC): counted under every fidelity; under
  `--fidelity silicon` the MOVE's write is dropped. `--strict=alu-move` stops at the first.
- `Risc::bus_hi` models the upper half of the bus as the GPU's own accesses leave it;
  every GPU load from the main bus latches it into G_HIDATA when the load lands (silicon
  only). `Stats::hidata_clobbers` counts G_HIDATA reads and STOREPs after such a load
  (every fidelity); `--strict=hidata` stops at the first. jsim does not model other
  masters' bytes in the undriven lanes.
- The run of `bench/gpuhaz` in jagemu `--fidelity silicon` now matches every row above
  except those bytes and the value of `D_FLAGS`.
